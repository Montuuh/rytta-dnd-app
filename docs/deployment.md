# Deployment and rollback

## Cloudflare Pages

The production host (ADR 047, ADR 055, RYT-158): the Pages project `rytta-app` in the Cloudflare
account of the project mailbox, served at https://rytta.app (canonical) and
https://rytta-app.pages.dev, and connected to the repository. The same account holds the
`rytta.app` registration and DNS zone, the Turnstile widget and Email Routing. It is static files
only: no Functions, no bindings and no secrets.

The first project, `rytta` (https://rytta.pages.dev), lives in the owner's personal Cloudflare
account. Its repository connection was removed on 2026-11-24 (Cloudflare connects a repository to
Pages in one account only), so it keeps serving its last build and no longer deploys. It stays
only as the source of the permanent redirect from `rytta.pages.dev` to `rytta.app`; never
delete it, or old links break.

Build settings (the project, Settings, Build):

- Build command `npm run build`; build output directory `dist`. No deploy command and no
  `wrangler` configuration: Pages publishes the output directory itself, honours the generated
  `_headers` file and falls back to `index.html` for unknown paths.
- Node 24 (`.nvmrc` and the CI workflow use 24; `engines` requires `>=24.13.0 <25`). Set the
  build variable `NODE_VERSION=24` if the image default differs.
- Production branch `main`, automatic deployments on. Preview branch deployments are set to
  None until a preview configuration that uses the staging Supabase project exists; previews
  must never use production, because they serve the `public` schema like any non-local host.
- The `VITE_` values are build variables of the project (Settings, Variables and secrets), not runtime bindings:
  Vite inlines them while building.

| Variable                        | Production and previews                                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `VITE_DATA_MODE`                | `supabase`                                                                                                         |
| `VITE_SUPABASE_URL`             | the project URL (staging project for previews)                                                                     |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | its publishable key (`sb_publishable_...`), never a secret key                                                     |
| `VITE_CONTACT_EMAIL`            | the public contact address (required: a live build fails without it)                                               |
| `VITE_OWNER_NAME`               | the person responsible for the service (required, same)                                                            |
| `VITE_SITE_URL`                 | the site's own https origin, no path; makes the share image absolute                                               |
| `VITE_BASE_PATH`                | leave unset: the site is at the root                                                                               |
| `VITE_TURNSTILE_SITE_KEY`       | the public Turnstile site key of the email sign-in bot check (RYT-157); its secret key lives only in Supabase Auth |

Nothing in the app assumes a subpath: asset URLs, the manifest (`start_url` and `scope` are
relative), the version check and the sign-in return address follow the base, and an unset base
is `/`. `VITE_SUPABASE_URL` also feeds the policy below, so the build allows exactly that origin.

Supabase and Google must know the new origin before sign-in works there:

- Supabase, Authentication, URL Configuration: set the Site URL to the site URL and add it, with
  its `?sb_flow_id=*` variant, to the redirect allowlist (the same exact-URL rule as in
  [Google and Supabase setup](setup-google-supabase.md)). Do the same on the staging project for
  the preview URLs.
- Google Cloud, the OAuth client: add the site origin to the authorised JavaScript origins. The
  authorised redirect URI stays the Supabase callback
  (`https://<project>.supabase.co/auth/v1/callback`), because the browser returns through
  Supabase, not directly.

Headers: `vite build` writes `dist/_headers` (generated by `scripts/lib/security-headers.mts`,
wired in `vite.config.ts`). Cloudflare applies it to every asset. It carries the Content Security
Policy, the other security headers and the caching rules; the policy takes its script hash from
the built `index.html` and its backend origin from `VITE_SUPABASE_URL`. A sample for a project at
`https://abc.supabase.co`:

```text
Content-Security-Policy: default-src 'self'; script-src 'self' 'sha256-<boot script>' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://abc.supabase.co; media-src 'self' https://abc.supabase.co; font-src 'self'; connect-src 'self' https://abc.supabase.co wss://abc.supabase.co; worker-src 'self' blob:; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

Why each non-obvious allowance exists: `'wasm-unsafe-eval'` for the 3D dice physics (WebAssembly,
not `eval`); `worker-src blob:` because the dice engine starts its worker from a blob;
`style-src 'unsafe-inline'` because Mantine injects theme styles at runtime and a static host
cannot nonce them; `data:` and `blob:` images for previews. Caching: `/assets/*` (hashed) is
`immutable` for a year; `/art`, `/bestiary`, `/tabletop`, `/icons` and `/vendor` are not hashed, so
they cache for a week plus a day of stale-while-revalidate (replace a picture under the same name
and it can look old for up to a week; rename it to publish at once); `/`, `/index.html`,
`/version.json` and the manifest are `no-cache` so the update notice sees new builds. Rules never
overlap on `Cache-Control`, because Cloudflare joins repeated headers. Limits: 100 rules, 2,000
characters per line; the policy line is far below that.

Check it locally: `npx playwright test --project=security-headers` builds the app at the root path
with a fixture backend, serves it with the generated `_headers` (`scripts/serve-with-headers.mjs`
applies the same rules as Cloudflare) and fails on any CSP violation across sign-in, sheet,
inventory, shops, bestiary, glossary, combat, tabletop, rest dice, portrait upload, language and
theme switches, the update notice and the privacy page. After the first real deployment, read the
response headers of `/` and of a hashed asset once to confirm Cloudflare applied them.

Owner checklist for the first deployment:

1. The build variables are empty today. Fill `VITE_DATA_MODE`, `VITE_SUPABASE_URL`,
   `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_CONTACT_EMAIL`, `VITE_OWNER_NAME` and `VITE_SITE_URL`
   before the first production build; leave `VITE_BASE_PATH` unset. Without them the build
   falls back to demo mode and the privacy pages show the owner as pending.
2. The production URL is `https://<project name>.pages.dev`; set it as `VITE_SITE_URL` when the
   project is created.
3. Add the new origin to Supabase Authentication (Site URL and redirect allowlist) and to the
   Google OAuth client's authorised JavaScript origins. Until then sign-in fails on the new
   site; the existing GitHub Pages site is unaffected.
4. Read the response headers of `/` once (see above). Done on 2026-11-18, together with a real
   Google sign-in on the new origin.

GitHub Pages was the previous host. Since 2026-11-18 Cloudflare is the only production site: the
Quality workflow no longer has a `deploy` job, the Supabase Site URL points at the Cloudflare
origin, and the old address is no longer updated. The workflow keeps `checks` on every push and pull
request and runs the four `e2e` shards on pull requests and manual dispatch. Cloudflare builds
main as soon as it is pushed and does not wait for the workflow, so changes reach main only
through a pull request whose checks and browser tests passed. Work collects on the integration branch
`next` in large commits, with one open pull request to main that runs the full checks on every
push; merging it is the release. Only an urgent production fix gets its own small pull request. A production build with
`VITE_DATA_MODE=supabase` fails while `VITE_CONTACT_EMAIL` or `VITE_OWNER_NAME` is empty; the CI
`checks` job builds in demo mode and the `e2e` builds pin both empty with
`RYTTA_ALLOW_UNPUBLISHED_OWNER=1` (set in `playwright.config.ts`, not a `VITE_` variable, so it
never reaches a bundle). No database migration runs from any build.

## Environments

Decision, costs and open items: [ADR 048](decisions/048-environments-staging.md). Three
environments exist today, all on free plans:

| Environment | Backend                                                       | Frontend                                | Data                             |
| ----------- | ------------------------------------------------------------- | --------------------------------------- | -------------------------------- |
| Production  | the production Supabase project, `public` / `private` schemas | https://rytta.app, built from main      | real campaigns                   |
| Staging     | a separate Supabase project (same organisation, eu-west-1)    | none yet                                | none: no data and no users       |
| PRE         | `pre` / `pre_private` schemas inside the production project   | local development and loopback previews | copied from production (ADR 007) |

- Staging has the full migration history, replayed from zero. It has no OAuth client, no
  redirect URLs and no seed yet, so nobody signs in there; checks run as actors inside
  rolled-back statements.
- PRE keeps working as [PRE environment](pre-environment.md) describes, and every migration
  still mirrors itself into it, until staging replaces it for local development.
- Configure providers, Google sign-in and exact Auth redirect URLs per project; see
  [Google and Supabase setup](setup-google-supabase.md). In-app invitations need no SMTP.
  Secrets stay server-side and are entered by the owner, never by tooling. PKCE callbacks return
  to the deployed base URL with query parameters; never implicit fragments.
- Backups: the free plan has no automated daily backups and no point-in-time recovery. Scheduled
  logical exports and a restore rehearsal into staging are still open.
- The nightly retention job is scheduled and active in production.

SQL sent to a hosted database is plain ASCII without backslash escapes (the delivery path decodes
backslash-u escapes in transit; build such text inside the database), and the committed LF
content is applied, never the CRLF working copy.

Applying a migration to the hosted databases, by hand until CI promotion exists:

1. Confirm the hosted history of staging and production, and that the migration is not applied.
2. Apply the committed LF file to staging.
3. Compare the md5 and length of the statement stored in staging's migration history with the
   file; any difference stops the procedure.
4. Verify the new objects in staging's catalog and run an actor-level check (the allowed role
   succeeds, anon, outsider, Player and cross-campaign DM are denied, as the migration requires)
   inside a statement that is rolled back.
5. In production, take a checksum of the existing data the migration must not change.
6. Apply the same file to production and repeat the md5 and length comparison.
7. Take the checksum again and compare it with step 5; repeat the catalog check. Log both
   applies, versions and checksums in the ticket evidence.

## Releases with a paired migration

Some database changes ship in two parts: an additive part applied ahead of time and a part the
deployed frontend cannot follow, applied together with the frontend release. Latest case
(ADR 043, RYT-104/105/107), completed on 2026-11-16: part 1
`20261120120000_items_decimal_catalogue_proposals.sql` (hosted version `20261116002653`) and
part 2 `20261121120000_items_player_authoring_close.sql` (hosted version `20261116081923`) are
both applied to production. Release order for a paired migration:

1. Confirm the hosted history has part 1 and not part 2, and that `private.money_scale()`
   returns 0 in production.
2. Push the frontend to main and wait for the host to build and publish it.
3. Apply part 2 right after the deployment finishes. Between the two steps the new frontend
   runs on whole gold (a typed cent amount is refused, never rounded) and the API still lets
   Players create items; no data is lost.
4. Verify `money_scale()` is 2, a Player receives `Forbidden` from `save_item_definition`, and
   the basic catalogue imports with cent prices. Retire the PRE rerun step in
   [PRE environment](pre-environment.md).

Before part 2, do not merge item definitions in production: a `merge` ledger row cannot be
parsed by the previous frontend. After part 2, rolling back to the previous frontend is not
safe: it parses gold as integers and cannot read cent amounts or `merge` rows. Fix forward
instead; a corrective migration can return both switches to their part-1 values but does not
remove amounts already stored with cents.

## Migration first: the sheet's concentration marker

`20261203120000_sheet_concentration.sql` (RYT-134) adds `character_vitals.concentration`. The
frontend that casts spells reads that column by name when it loads a sheet, so against a database
without it every character sheet fails to load. Apply the migration to production first, confirm
the column exists and `set_character_vitals` takes `change_concentration` and `new_concentration`,
and only then publish the frontend. The frontend already in production keeps working after the
migration: it calls `set_character_vitals` with the thirteen original arguments, which leaves the
marker untouched. Rolling the frontend back after the migration is safe for the same reason.

## Backups

The free database plan keeps no backups (checked in the project console on 2026-11-18), so the
repository takes its own. The `Backup` workflow (`.github/workflows/backup.yml`) runs once a day
and on manual dispatch: it dumps roles, schema and data of production with the Supabase CLI,
encrypts them with [age](https://age-encryption.org) to the owner's public key inside the runner,
deletes the plain files and keeps only `backup.tar.age` (and its SHA-256) for 14 days as a workflow
artifact. It does nothing until both the secret `BACKUP_DB_URL` and the variable
`BACKUP_AGE_RECIPIENT` exist, and it fails rather than upload anything that is not encrypted.

The repository is public since 19 November 2026, so artifacts are downloadable by anyone; only the
holder of the private key can read them. The workflow was disabled on 2026-11-20 after two
unencrypted artifacts were exposed and deleted (docs/evidence/RYT-122/owner-checks-2026-11-20.md).

Owner steps, once:

1. In the Supabase console of the production project, open Connect and copy the session pooler
   connection string (it works over IPv4, which the workflow runner needs); put the database
   password in it. Reset the password there first if it is not known.
2. In the repository, Settings, Secrets and variables, Actions: add the secret `BACKUP_DB_URL`
   with that string. It is a secret: never commit it, paste it in an issue or type it in a chat.
3. On your own computer, install age and run `age-keygen -o rytta-backup.key`. Keep that file in
   your password manager (it is the only way to read a backup; losing it loses every backup). It
   prints the public key, `age1…`.
4. Add the repository variable (not a secret) `BACKUP_AGE_RECIPIENT` with that public key.
5. Enable the workflow (`gh workflow enable Backup` or the Actions tab), run it once by hand and
   check that the artifact holds only `backup.tar.age` and `backup.tar.age.sha256`.

To read a backup: download the artifact, check the SHA-256, then
`age -d -i rytta-backup.key backup.tar.age | tar -x` gives `roles.sql`, `schema.sql`, `data.sql`
and `MANIFEST.txt`. Delete the plain files when done.

Not covered: files in Storage (portraits, maps, item pictures) are not in the dump. Restore is
not rehearsed yet. Staging holds synthetic data only (ADR 048), so loading a production dump into
it is the owner's decision; the alternative is a rehearsal into a throwaway local database with
the same steps (RYT-116). Until a rehearsal exists, treat the backup as unproven.

## Vercel fallback

Vite preset, npm ci, npm run build, output dist, base /. Same hash routes work without
rewrites. Set public environment variables and allowlist the stable domain in Supabase.
Preview domains need an explicit auth policy. No Vercel project is provisioned now.

## Rollback

Frontend: dispatch the last known-good revision, then verify public URL/data compatibility.
Database: forward corrective migrations; never delete applied migrations or reset production.
Use tested backups before destructive changes. Prefer expand/contract schema changes.
